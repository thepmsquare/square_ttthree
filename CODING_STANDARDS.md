# repository coding standards & architecture guidelines

this document outlines the mandatory architectural patterns, naming conventions, and design guidelines for this repository.

---

## 1. user-facing text & lowercase rule

- **lowercase requirement**: all user-facing application text (messages, error descriptions, and standard response messages) generated by the application **must be in lowercase**.
- **case preservation**: all user-inputted text (e.g., input parameters, codes) and text received from external api responses **must preserve their original case**.

---

## 2. api response formatting & messages

- **centralized messages (`<module_name>/messages.py`)**: all user-facing response messages must be defined in `messages.py` inside the `messages` dictionary.
- **standard envelope**: all http responses must be wrapped using the `get_api_output_in_standard_format` helper function from `square_commons`.
- **response model validation**:
  - every outgoing api response payload must be validated by instantiating its corresponding `ResponseModel` pydantic class first.
  - the validated model is converted via `.model_dump()`, passed into `get_api_output_in_standard_format(data=...)`, and returned as a `JSONResponse`.

---

## 3. router layer (`<module_name>/routes/`)

- **router as an index**: route files act solely as an index of endpoints for a specific feature module. they must contain **no business logic**.
- **function naming**: all functions bound to api endpoints must start with the prefix `api_` (e.g., `api_create_resource`, `api_get_resource`).
- **path prefixes**: path prefixes in `APIRouter` initialization must always start with a leading slash `/` (e.g., `prefix="/api/v1"`).
- **execution flow**: route handlers catch exceptions (`HTTPException` and generic `Exception`), delegate execution to a corresponding `logic_` function, and return its `JSONResponse`.

---

## 4. logic layer (`<module_name>/logic/`)

- **business & state logic**: all business logic, state management, state transitions, and singleton services (e.g., `resource_manager`) reside in the `logic/` package.
- **function naming**: logic functions called by routes must start with the prefix `logic_` (e.g., `logic_create_resource`, `logic_get_resource`).
- **logging decorator**: all `logic_` functions must be decorated with `@auto_logger()`.
- **response construction**: logic functions perform business operations, instantiate the response model, package it via `get_api_output_in_standard_format`, and return the `JSONResponse`.

---

## 5. models packaging (`<module_name>/models/`)

the `models` package is divided into two distinct subpackages:

### 5.1 api models (`models/api/`)

- contains pydantic models for http request and response payloads.
- each router has a corresponding module file (e.g., `models/api/<feature_name>.py`).
- **naming conventions**:
  - **request payloads**: must end with the `RequestModel` suffix (e.g., `FeatureCreateRequestModel`).
  - **response payloads**: must end with the `ResponseModel` suffix (e.g., `FeatureCreateResponseModel`, `FeatureGetResponseModel`).

### 5.2 internal models (`models/internal/`)

- contains internal domain entities, data classes, and enums (e.g., `EntityModel`, `EntityStatus`).
- **enums**: all status strings and state constants should be represented as string enums inheriting from `(str, Enum)` (e.g., `EntityStatus.NOT_STARTED = "not_started"`).

---

## 6. logging & configuration (`square_logger`)

- use the logger instance (`logger`) and decorator (`@auto_logger()`) exposed in `<module_name>.configuration`.
- log lifecycle events (creation, connections, cleanups) at `INFO` level.
- log error tracebacks at `ERROR` level.

---

## 7. testing standards (`tests/`)

- tests are written using `pytest` and `anyio` (`@pytest.mark.anyio`).
- fixtures in `tests/conftest.py`:
  - `get_patched_configuration`: loads test-specific configuration (`config.testing.ini`).
  - `create_client_and_cleanup`: provides an `httpx.AsyncClient` tied to the fastapi app instance.
- all endpoints must have automated tests verifying:
  - success payloads and http status codes.
  - case-insensitive lookups (where applicable).
  - error responses and 404 formatting.
